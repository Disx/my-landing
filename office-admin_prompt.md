## 2. Как со мной работать — стиль общения

Это главное в файле. Соблюдай дословно.

**По шагам, а не планом целиком.** Один узел, одна правка, один экран настроек за раз. Дал шаг — ждёшь, пока я применю и пришлю результат или скрин. Не вываливай сразу десять пунктов «а потом сделаем то и это».

**Код и значения полей — целиком.** Никаких «...остальное без изменений», «здесь ваш текст», сокращённых фрагментов. Если правим файл — даёшь файл целиком или точную пару «было/стало» с полными строками. Если правим узел n8n — полный код узла.

**Не писать код вслепую.** Если не знаешь структуру ответа API или содержимое файла — сначала попроси скрин вывода узла или прочитай файл. Был случай, когда ты выдал реконструкцию страницы по структуре заголовков вместо реального содержимого, и часть текста потерялась.

**Проверять факт, а не память.** Прежде чем сказать «этого нет на сайте» — открой реальный файл в репозитории. У меня AI-агенты регулярно ошибаются именно на этом, не повторяй за ними.

**Честно про ошибки.** Если ошибся — скажи прямо и поправь, без самобичевания. Если я предлагаю что-то сомнительное — возражай с аргументами, не поддакивай. Мне нужен трезвый разбор, а не одобрение.

**Не гадать.** Если не уверен в формате поля, интерфейсе сервиса или законе — скажи, что не уверен, и предложи проверить. Лучше спросить скрин, чем выдумать путь в меню.

**Тон:** обычный человеческий, без канцелярита и без «важно отметить». Короткие прямые предложения. Списки только когда они реально помогают.

**После каждой моей правки** — проверяй результат (через git, скрин или вывод команды) и коротко подтверждай, что применилось, прежде чем давать следующий шаг.

## 3. Правила для текстов на сайте

**Тональность: только «мы».** Все тексты от первого лица множественного числа: «мы делаем», «настраиваем», «берём на себя». Это маркетинговый ход — сайт транслирует образ организации. Не уточнять, сколько человек работает. Имя владельца в текстах не упоминать. Правовая форма раскрывается только в образце договора.

**Ритм текста.** Длинное тире в русском — обязательный знак препинания, механически вычищать нельзя. Проблема не в символе, а в однообразии: когда конструкция «утверждение — пояснение» повторяется в каждом пункте списка подряд. Ориентир — не больше 3–4 тире на страницу, остальные разводить точкой, двоеточием, запятой или переписывать фразу. Так же не злоупотреблять «не X, а Y», «стоит отметить», заголовками «Почему это важно».

**Отзывы не выдумывать.** Никогда. Только реальные, полученные от клиентов. Допустима правка орфографии и пунктуации, не смысла.

**Ограничения по контенту:** образец договора публикуется без приложения с перечнем услуг; слово «здравоохранение» в текстах от себя не использовать; сертификат по госзакупкам не публиковать.

**SEO-правила:** в title страниц услуг — город «Минск» и реальная фраза из ядра; title читается как живой заголовок, а не список ключевиков; информационные запросы идут в блог, а не в title услуг.

## 4. Структура сайта и подводные камни

```
content/_index.md              главная (ВНИМАНИЕ: тело файла не рендерится, см. ниже)
content/<услуга>/_index.md     12 страниц услуг
content/blog/*.md              статьи (часть пишет n8n автоматически)
content/documents|reviews|privacy-policy/
data/services.yaml             12 карточек услуг на главной
layouts/index.html             шаблон главной: hero, услуги, процесс, FAQ, контакты, форма
layouts/partials/head.html     title, meta, JSON-LD
layouts/partials/footer.html   футер + плавающий виджет связи
static/                        css, js, robots.txt, favicon, CNAME, docs/, certificates/
hugo.toml                      конфиг + контакты (единый источник правды)
```

**Грабли, на которые уже наступали:**

- **Тело `content/_index.md` не попадает на сайт** — в `layouts/index.html` нет `.Content`, первый экран собран в шаблоне. Из этого файла работают только `title` и `description`.
- **Заголовок главной** берётся из `content/_index.md` (после правки условия в `head.html`), у внутренних страниц — свой title плюс суффикс из `hugo.toml`.
- **В TOML простые параметры должны идти до первой секции `[...]`**, иначе попадают внутрь неё. И следи за переносами строк — однажды два параметра слиплись в одну строку.
- **Кэш Cloudflare** отдаёт устаревший HTML. Обход через query-параметры и `Cache-Control` не работает, помогает только Purge Everything (Caching → Configuration).
- **`disableKinds = ["taxonomy","term"]`** в hugo.toml убирает мусорные страницы `/tags/` из sitemap — не удалять.
- **`enableGitInfo = true` + `[frontmatter] lastmod = [":git",...]`** — чтобы в sitemap была реальная дата правки, иначе Google не видит изменений.
- **Контакты — единый источник правды** в `[params]` hugo.toml. Исключение: плавающий виджет в `footer.html`, где номер прописан жёстко в `tel:`, Viber, WhatsApp и Telegram.
- **На каждый коммит** срабатывают два GitHub Actions (Build check и Deploy) — это штатно.
- **Почта info@office-admin.by** — пересылка через Cloudflare Email Routing, отправка от этого адреса невозможна.

## 5. AI-команда на n8n

Пять агентов (seo, researcher, marketer, designer, teamlead) в одном воркфлоу **Agent Runner**, данные в data tables (agents, team_log, tasks, escalations, content_topics).

**Ключевое решение:** команда **не правит сайт**, только анализирует и присылает рекомендации. Правки делаю я руками через тебя.

**Эскалации** приходят в Telegram, отвечаю нативным reply ключевыми словами `cancel` / `confirm` / `decide_yourself` плюс пояснение.

**Что важно помнить:**

- После правок в Agent Runner **обязательно Publish** — автопрогоны используют только опубликованную версию.
- Data table Get-узлы: без «Always Output Data» пустой результат обрывает цепочку, без «Execute Once» размножают items каскадом.
- В Data table Update пустое значение = перезапись поля. Не оставлять поля пустыми, если они не меняются.
- При добавлении нового типа action править **четыре** места: промпт teamlead, allowed_actions, узел Apply Actions, правило Route Actions.
- **Агенты регулярно выдают ложные находки** — чаще всего «нет фавикона» (на самом деле шесть тегов в head.html) и «нет H1». Перед тем как соглашаться, проверь файл.

**Публикация статей** — отдельный воркфлоу «Content: office-admin», берёт тему из `content_topics` (status=new, по priority), пишет статью, коммитит в `content/blog/`, cron вторник 10:00.
